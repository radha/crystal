# Crystal GC research — bdwgc internals & comparative designs (2026-06-11)

## Executive summary

This report synthesizes a deep investigation into how Crystal's garbage collection works, how the Boehm-Demers-Weiser collector (bdwgc) it links is actually built and behaves, and how compiled statically-typed peers (Go, Nim/Swift, OCaml/GHC, D/Julia/Immix/MMTk, and prior bdwgc embedders) solve the same problems. It feeds a curated set of optimization opportunities, each run through adversarial verification against the *real* libgc on this machine (homebrew bdw-gc 8.2.12, macOS ARM64) and against Crystal's actual source. The single most important empirical finding: **default (non-`preview_mt`) Crystal binaries mark on one CPU core forever** — bdwgc ships with parallel marking compiled in, but marker threads only spawn lazily at the first wrapped `pthread_create`, which never happens in single-threaded programs; calling `GC_start_mark_threads()` once at init gives a measured 1.86x–2.85x faster mark phase. Of twelve candidate opportunities, six survived verification; the rest are documented with their refutations (most notably a reproduced heap-corruption double-free when making GMP limbs atomic) so they are not re-litigated. The structural ceiling — conservative non-moving Boehm with every class heap-allocated and no escape analysis — is real, and the highest-leverage long-term lever is allocation-volume reduction (escape analysis), which pays off independent of the collector.

## How bdwgc works

bdwgc on this machine is **master-equivalent 8.2.12** (homebrew, CMake build with `-Denable_cplusplus=ON -Denable_large_config=ON`), built with `PARALLEL_MARK`, `THREAD_LOCAL_ALLOC`, `USE_MMAP`+`USE_MUNMAP`, `GCJ`/typed-object support, disclaim finalization, `ALL_INTERIOR_POINTERS`, and `NO_EXECUTE_PERMISSION`. The collector is a conservative, non-moving, stop-the-world mark-sweep that runs **inside allocation calls** — there is no dedicated GC thread (only optional in-pause marker threads and, on macOS incremental mode, a Mach-exception handler thread).

**Allocation internals (allocation researcher).** A two-level allocator: small objects (≤ `MAXOBJBYTES` = `HBLKSIZE`/2 = 2048 B; `HBLKSIZE`=4096) are carved from 4 KB heap blocks dedicated to a single (size, kind) pair; larger requests round up to whole blocks via `GC_allochblk` over 61 size-binned free lists. Sizes are managed in **16-byte granules** (on 64-bit). Object kinds: `PTRFREE=0` (not scanned, not zeroed — the `GC_malloc_atomic` kind), `NORMAL=1` (scanned, **guaranteed zeroed** via `ok_init`), and `UNCOLLECTABLE`. `GC_malloc(n)` = `GC_malloc_kind(n, NORMAL)`; `GC_malloc_atomic(n)` = `GC_malloc_kind(n, PTRFREE)`. With `THREAD_LOCAL_ALLOC`, `GC_malloc_kind` does a TLS lookup then pops from per-thread tiny free lists (25 classes, ≤384 B), refilling ~4 KB at a time via `GC_generic_malloc_many` under one lock acquisition (so the global lock is amortized to roughly one per ~85 allocs at 48 B). Sweeping is lazy and header-only at GC end; `NORMAL` objects are cleared at allocation time. Two findings matter most for Crystal: (1) the default **`EXTRA_BYTES`=1** (because `ALL_INTERIOR_POINTERS` is on) makes every exact-16n-byte request consume 16(n+1) bytes — *measured*: `GC_size(GC_malloc(16))`=32, 32→48, 64→80, a 100%/50%/25% footprint tax; and (2) Crystal's codegen memsets buffers that `GC_malloc` already zeroed. On Darwin, `THREAD_LOCAL_ALLOC` uses `pthread_getspecific` (Darwin is excluded from bdwgc's compiler-TLS whitelist), not `__thread`. Measured single-threaded on Apple M-series: `GC_malloc` 32 B ≈ 8.0 ns, atomic ≈ 7.3 ns, `GC_malloc_many` pool pop ≈ 5.1 ns; 8 KB allocs ≈ 1.05 µs dominated by GC pacing (a full GC every ~59 large allocs at `free_space_divisor`=3).

**Marking & collection (marking researcher).** The mark loop (`GC_mark_from`, "the most performance critical routine in the collector") loads every `ALIGNMENT`-aligned word in a range, range-checks it against plausible heap bounds, resolves it through a two-level block-header table with a per-block displacement map, sets a mark bit, and pushes a (start, descriptor) entry. Mark descriptors come in four classes: `GC_DS_LENGTH` (conservative whole-object scan), `GC_DS_BITMAP` (a 62-bit pointer bitmap, scanning only set bits), `GC_DS_PROC` (custom mark proc), `GC_DS_PER_OBJECT` (descriptor in object or in a first-word "vtable" — the gcj design). `PTRFREE` has descriptor 0 and is never scanned. Stop-the-world: Linux uses suspend signals + semaphore handshakes; **macOS iterates registered threads with `thread_suspend`/`thread_get_state`/`thread_resume` (no signals)**, pushing x0–x28+lr from Mach thread state on ARM64. `PARALLEL_MARK` turns the global mark stack into a work-stealing queue (markers = min(ncores,16)−1), but **markers start only at the first wrapped `pthread_create` or an explicit `GC_start_mark_threads()`** — so single-threaded programs always mark serially. Any time-limited (incremental) mark disables parallel marking. The initial mark stack is only 4096 entries; overflow forces `MS_INVALID` and a whole-heap rescan (a perf cliff, though the stack self-doubles for later GCs). The collection trigger heuristic weights composite (scanned) heap **8× heavier than atomic** heap and counts **2× total stack bytes**: `scan_size = 2·composite + atomic/4 + (2·stack + roots)`, threshold = `scan_size / free_space_divisor` (default 3). Crystal's pain point: it pushes every suspended fiber stack via `GC_push_all_eager`, a serial word-by-word scan during the root-push phase inside the pause.

**Typed / advanced API (precise researcher).** Homebrew libgc 8.2.12 **already exports** `GC_gcj_malloc`, `GC_init_gcj_malloc`, `GC_make_descriptor`, `GC_malloc_explicitly_typed`, `GC_new_kind`, `GC_new_proc`, `GC_finalized_malloc`, `GC_register_disclaim_proc`, `GC_register_finalizer_no_order`, and `GC_register_displacement`. `GC_malloc_explicitly_typed` stores the descriptor in the object's last word (+8 B/obj), forbids `GC_realloc`, and — critically — its custom kind has **no thread-local free lists** (`THREAD_FREELISTS_KINDS`=2/3; custom kinds start at 3/4), so every small typed alloc takes the global lock. The far better runtime path is the **gcj kind** (`GC_gcj_malloc`): a first-word pointer to a static per-type structure holding the descriptor, zero per-object overhead, dedicated thread-local `gcj_freelists`, and proven by Mono's Boehm backend (`mono/metadata/boehm-gc.c` uses `GC_init_gcj_malloc` + `GC_make_descriptor`). Custom kinds (`GC_new_kind`/`GC_new_proc`, max 64 procs) support a precise-heap/conservative-stack hybrid with per-type incremental migration; mark procs must tolerate being called on cleared free-list objects. Finalization: `GC_register_finalizer*` makes every GC walk the entire finalizable-object hash table twice and transitively mark from each dying object (Crystal's finalizable objects need two GC cycles to free); `_no_order` uses a null mark proc; the **disclaim** API runs a callback during sweep (~6× faster in bdwgc's `disclaim_bench`, but under the allocator lock and the kind's blocks are scanned unconditionally every cycle). `GC_realloc` shrink: if new ≥ old/2 and it fits, returns the **same pointer** after zeroing the tail (reclaims nothing); below half it allocates+copies+frees.

**Tuning surface + empirical probe (tuning researcher).** A live FFI probe of the linked libgc from Crystal confirmed: **version 8.2.12, `GC_parallel`=0** (serial marking in every default process), `all_interior_pointers`=1, `free_space_divisor`=3, `full_freq`=19, `time_limit`=999999 (UNLIMITED — `PARALLEL_MARK` builds default to unlimited because the parallel marker cannot be interrupted), incremental off but `GC_enable_incremental` works at runtime (MPROTECT_VDB compiled in for macOS ARM64, with `incremental_protection_needs`=3 meaning even pointer-free buffers get write-protected during incremental cycles). Calling `GC_start_mark_threads()` flipped `GC_parallel` to 7 and cut 20 full GCs over a 26.6 MB heap from 59.7 ms to ~20 ms. Default startup heap is small (`MINHINCR`·`HBLKSIZE`); `GC_INITIAL_HEAP_SIZE=64M` eliminated all collections for a 32 MB workload. Tuning env vars read at `GC_init`: `GC_INITIAL_HEAP_SIZE`, `GC_FREE_SPACE_DIVISOR`, `GC_MARKERS`, `GC_ENABLE_INCREMENTAL`, `GC_PAUSE_TIME_TARGET`, `GC_UNMAP_THRESHOLD` — all work today with zero code changes (except on Windows, where bdwgc's cmake adds `-DEMPTY_GETENV_RESULTS` and ignores them). Several wins are **compile-time only** and unreachable via the runtime API: `DONT_ADD_BYTE_AT_END` (removes the `EXTRA_BYTES` tax), `INITIAL_MARK_STACK_SIZE`, `THREAD_FREELISTS_KINDS`, `HBLKSIZE`, the Darwin TLS whitelist.

## How Crystal uses it

Ground truth from the three Crystal-side researchers, with file:line anchors.

**Integration layer (`src/gc/boehm.cr`, `src/gc.cr`).** Crystal's GC integration is a thin, almost tuning-free FFI layer. `GC.init` (`src/gc/boehm.cr:211-261`, the first call in `Crystal.main`) does only: `GC_set_handle_fork(1)` (`:213`), `GC_init` (`:215`), an RWLock init (preview_mt), `GC_set_start_callback` (acquires the Crystal write lock under preview_mt), a chained `GC_set_push_other_roots` "before_collect" hook that pushes every suspended fiber's stack via `GC_push_all_eager` and (preview_mt) refreshes per-thread `GC_set_stackbottom`, and a `GC_set_warn_proc` filter. **Crystal sets zero performance knobs** — no `GC_set_free_space_divisor`, `GC_set_markers_count`, `GC_start_mark_threads`, `GC_enable_incremental`, `GC_set_all_interior_pointers`, or typed allocation anywhere in `src/` (`GC_set_max_heap_size` and `GC_collect_a_little` are bound at `boehm.cr:112`/`:94` but never called). `GC.malloc`/`malloc_atomic`/`realloc`/`free` (`boehm.cr:190-209`) wrap the FFI call in `Crystal.trace :gc` blocks that compile to a bare `yield` (zero overhead) without `-Dtracing` (`src/crystal/tracing.cr:306-312`) — confirming the roadmap's VERIFY-FIRST item: **`Crystal.trace` fully compiles out** of the allocation wrappers in default builds. Finalizers use `GC_register_finalizer_ignore_self` with a per-type proc (`boehm.cr:330-343`); the proc is a non-capturing static (`->(obj, data) { obj.as(T).finalize }`), confirming the roadmap's add_finalizer concern. Fiber stacks are 8 MiB `mmap` regions outside the GC heap, pooled per scheduler; suspended ones are pushed conservatively/eagerly from `[stack_top, stack.bottom]` each collection (`boehm.cr:226-242,482-484`; `src/fiber.cr:386-389`). Min supported libgc is 8.2.0+.

**Codegen allocation paths (`src/compiler/crystal/codegen/`).** Every allocation is a call to `__crystal_malloc64`/`__crystal_malloc_atomic64`/`__crystal_realloc64` (`codegen.cr:14-16`) → plain Crystal funs (`src/gc.cr:17-47`) → `GC.malloc`. **No `@[AlwaysInline]`** anywhere in the chain (debug builds execute 3 nested calls/alloc); at `-O1 --single-module` LLVM inlines to one `tail call ptr @GC_malloc(i64 N)`, but the `declare ptr @GC_malloc(i64)` carries **zero LLVM attributes** (no `noalias`/`allocsize`/`allockind`/`alloc-family`), so LLVM cannot delete dead allocations or fold memsets. Class allocation (`allocate_aggregate`, `codegen.cr:2250-2264`) picks `GC_malloc` if any ivar `has_inner_pointers?` else `GC_malloc_atomic`, then `pre_initialize_aggregate` (`:2266-2276`) **always memsets the full object**; `generic_array_malloc` (`:2350-2361`) also always memsets the buffer — so every pointer-containing class instance and Array/Hash buffer is **zeroed twice** (once by `GC_malloc`'s NORMAL contract, once by codegen), and the redundant memset survives `-O1`/`-O3`. `has_inner_pointers?` (`types.cr:54-99`): Void/Pointer/Proc/classes→true, primitives/enums→false, aggregates recurse, unknown→true (conservative). Closure environments (`codegen.cr:2127-2167`) are malloc'd unconditionally at function entry whenever any local is closured (`:2054-2059`) and **per-Yield** for closured block vars (`:1744-1755`) — per-iteration heap allocation in capturing loops. Tuples/structs/unions are stack-`alloca`'d (no union boxing). `String.new(capacity)` uses `GC.malloc_atomic` + a shrink `GC.realloc` (`string.cr:265-287`).

**Allocation-pressure map (`crystal-alloc-pressure`).** Hot per-op allocators: every String substring/concat/transform allocates a fresh String; `Char#to_s` allocates a new 1-char String per call (no interning); most iterator combinators are classes (one alloc per chain link); every `raise` captures a callstack (`Array(Void*).new(32)`) plus the exception and a `LibUnwind::Exception`; `spawn` allocates a Fiber + closure env. Existing mitigations: JSON `StringPool` for keys (absent in YAML), thread-local PCRE2 `match_data`, reusable `IO::Buffered` 32 KB atomic buffers, 63 stack `uninitialized UInt8[N]` sites, `String::Builder` finalizing its buffer into a String zero-copy, Hash compaction-instead-of-resize. Measured (non-release, macOS ARM64): 1M 7-byte strings (~32 MB) → 52 collections while heap grew 262 KB→786 KB (~one GC per ~615 KB); pointer-bearing 16 B class ~14 ns/alloc incl. GC; full collect 0.04 ms on 768 KB vs 0.79 ms on 64 MB — **pause cost scales with live heap, collection frequency scales with heap/3**. Single-threaded scheduler makes one `GC_set_stackbottom` FFI call per fiber resume (`scheduler.cr:113`, with a `GC_self_thread_inner` lookup inside libgc), even though the thread handle is already cached for preview_mt use.

## GC in other compiled statically-typed languages

**Go** — concurrent, precise, non-generational, non-compacting tri-color mark-sweep + a tcmalloc-derived allocator. Wins decompose into three separable layers: (1) **allocator layout** — per-P `mcache` (lock-free fast path: `nextFreeFast` is a `TrailingZeros64` over a free-slot bitmap), 67 size classes, bitmap-swap sweep, a 16-byte tiny allocator (−12% allocs/−20% heap on a json benchmark); (2) **precision** — `noscan` spans (the `GC_malloc_atomic` analog, zero per-object metadata) are marked but never scanned; per-word pointer bitmaps enabled Green Tea (Go 1.26, span-batched FIFO scanning + AVX-512, 10–40% GC-CPU reduction, motivated by ≥35% of mark time being memory stalls); (3) **the hybrid Dijkstra+Yuasa write barrier** (per-P 512-entry buffer, register-preserving asm) eliminated STW stack rescans, targeting <50 µs pauses. The pacer triggers at `liveHeap·(1+GOGC/100)` (default GOGC=100 doubles headroom and halves GC CPU). Escape analysis keeps allocation volume down *before* the allocator is touched. **Transferable lesson:** heap-to-stack conversion is the single biggest lever Crystal lacks — every Crystal Reference/closure-env is an opaque FFI `GC_malloc` LLVM can never eliminate; volume reduction compounds (cuts per-alloc cost *and* GC frequency). Crystal's preview_mt per-allocation RWLock is a direct anti-pattern vs Go's lock-free mcache.

**Nim ARC/ORC + Swift ARC** — Nim ARC is compile-time scope-based RC injected as `=destroy`/`=sink`/`=copy` hooks with move optimization; ORC adds a Bacon-Rajan trial-deletion cycle collector (default since Nim 2.0). Nim's own docs concede async/closures cycle and leak under pure ARC. Swift ARC is always-on **atomic** RC; Swift programs spend on average 32% (clients 42%) of runtime in RC ops, removing the atomics alone gives 25% — and >99% of objects are single-thread-accessed. Academically, naive RC is ~30% slower than tuned mark-sweep; optimized RC reaches parity but stays ~13% behind production generational tracing until RC-Immix re-adds copying. The key stat: **71% of RC ops hit newly-allocated objects, <10% survive** — young-object handling decides throughput, not RC-vs-tracing. **Transferable lesson:** compile-time RC is a structural non-starter for Crystal (heap closures, shared-everything fibers/channels, class-based stdlib, no destructors); the portable equivalent of ARC's elision analysis is **escape analysis to stack-allocate non-escaping instances** — the same young objects Nim's `injectdestructors` makes free, at zero semantic change.

**OCaml + GHC** — both reach ~2 ns allocation via bump-pointer nurseries, enabled by two things Crystal lacks: **precise roots and object movability**. OCaml's `Alloc_small` is "`young_ptr -= size`; limit-check; write header"; precision comes from uniform value tagging (low bit = int vs pointer); minor collection is copying (cost ∝ survivors only); a `caml_modify` write barrier maintains the remembered set. Multicore OCaml's decisive result: they built both a concurrent minor collector (needs read barriers, breaks the C API) and a **stop-the-world parallel minor collector** — ParMinor won (3.5% seq overhead, **no C API change**). GHC reaches the same shape with block-structured per-capability nurseries, `mut_list` remembered sets, **pinning** as the FFI escape hatch (ByteString pinned, ShortByteString/Text deliberately unpinned to avoid fragmentation), compact regions (excluded from GC traversal), and an optional concurrent non-moving old-gen collector (8.10, "3× pauses for ≤10% throughput"). Local measurement: bdwgc `GC_malloc` 7.9–10.5 ns/alloc vs ~2.3–2.6 ns for a simulated bump nursery — a **~3× mutator-side gap** that tuning cannot close (the rest is structural: mark cost scales with whole heap vs survivors). **Transferable lesson:** without movability the reachable wins are precise/typed heap marking, allocation-rate reduction, incremental mode, and arena/compact-region APIs; if a nursery is ever built, **per-context nurseries + STW parallel minor GC** is the FFI-compatible multicore design, with pinning for C-escaping objects.

**D / Julia / Immix / MMTk** — D druntime is the closest existence proof of a "mostly precise" retrofit: `gc:precise` is the *same* conservative mark-sweep with a flag, the compiler emits per-type pointer bitmaps (`__traits(getPointerBitmap)`), stacks/registers stay conservative; **measured cost 0–10% *slower*** — the payoff is false-retention elimination, not speed. D also shipped **default-on parallel marking (DMD 2.087)** and a fork()-snapshot concurrent mark. Julia shows fully-precise non-moving generational: 2-bit header states, sticky old marks, per-thread remsets from an inlined write barrier (~6 instructions), per-datatype pointer-offset arrays (u8/u16/u32, denser than bitmaps), Chase-Lev work-stealing, and an in-tree third-party-GC interface with an MMTk Immix backend. Immix (32 KB blocks/128 B lines, bump-into-holes, opportunistic evacuation, natural pinning) beats canonical collectors 5–25%. Critically, the Immix paper shows sticky-mark-bit generational over **free-list mark-sweep** (which is exactly bdwgc's incremental mode) "does not improve sufficiently to justify its use" while over Immix it almost uniformly wins. **Transferable lesson:** the structural win is heap *organization* (Immix), not bolting generational onto bdwgc; the prerequisite, no-regret codegen work is **emitting per-type pointer-layout tables** (reusable across bdwgc typed-alloc, custom mark procs, and a future Immix/MMTk backend); conservative-stack + precise-heap is the proven sweet spot. The ISMM'25 Julia/MMTk "conservative pinning with valid-object bits" is the escape hatch if moving GC is ever wanted.

**bdwgc prior art (Mono→SGen, Guile, ysbaddaden's Crystal Immix)** — three proven paths and one dead end. **Stay-and-tune:** Guile, Unity, Inkscape, w3m stayed on bdwgc for decades; Unity ships bdwgc's **incremental mode default-on** (3 ms slices), proving latency viability; Guile tunes `GC_set_all_interior_pointers(0)`, `GC_set_finalize_on_demand(1)`, heap presizing. **Precise-marking-on-Boehm:** gcj and Mono's Boehm backend both used `GC_init_gcj_malloc` + `GC_make_descriptor` for precise heap marking with conservative stacks — the cheapest structural win, and the API still ships. **Replace:** Mono built SGen (generational copying, 4 KB TLABs, card-table barriers, precise heap/conservative stacks) because Boehm's conservatism blocked compaction; Scala Native swapped Boehm→Immix→Commix; Guile is mid-migration to **Whippet** (feature-complete Oct 2025), whose documented bdwgc indictment — global alloc-lock kills MT scaling, no ephemerons, no compaction, mprotect generational mode made things **20% slower**, unhackable codebase — is the best modern reference. **Dead end:** ysbaddaden/gc (pure serial Immix in C, runs via the `-Dgc_none` pluggable interface from PR #5314) worked but stalled because the serial collector is "significantly slower than BDWGC", macOS support never finished, and precise marking via LLVM stack maps was judged too slow/costly. **Transferable lesson:** don't rewrite bdwgc serially — extend it (typed marking, tuning, parallel mark) or adopt Whippet (it has a bdwgc-API shim; Guile validates the exact "conservative embedder" profile Crystal has). Crystal's MT GC contention is documented (#10372: `--release` slower than debug at 8 threads under allocation pressure).

## Confirmed opportunities (ranked by corrected impact × breadth)

Only opportunities with `confirmed=true` (premise AND feasibility verified). Impact figures are **post-skepticism (corrected_impact)**, not the original estimates.

### 1. Start bdwgc parallel marker threads in `GC.init`
- **What & where:** Bind `GC_start_mark_threads` and `GC_set_markers_count` in LibGC; call `GC_start_mark_threads()` right after `LibGC.init`, and `GC_set_markers_count` *before* `LibGC.init`. `src/gc/boehm.cr:211-224` (`GC.init`), new bindings near `boehm.cr:89-120`. Restart markers in non-exec fork children via `Process.after_fork_child_callbacks` (`src/crystal/system/unix/process.cr:223`).
- **Mechanism + reference design:** Homebrew/distro libgc is built with `PARALLEL_MARK`, but marker threads spawn only at the first wrapped `pthread_create` or an explicit `GC_start_mark_threads()` (lazy-start at `pthread_support.c:2899-2903`) — so every default single-threaded Crystal binary marks on one core. Full (non-incremental) collections use `GC_never_stop_func` and are fully parallel-markable. Reference: **D shipped parallel marking default-on in DMD 2.087**.
- **Corrected impact:** **1.5–2.9× pause reduction for heaps ≥ ~20 MB** (measured 1.86× at ~20 MB live, 2.85× at ~160 MB on a 4P+4E M-series; the original 3×@26.6MB did not reproduce — likely a dead-root benchmark bug). Whole-program ~2–10% wall on allocation-heavy programs, ~0 for small-heap CLIs. Linux holds by construction (Debian/Alpine 8.2.12 + Crystal's official static libgc all build threads=posix with `PARALLEL_MARK` default-on).
- **Risk:** Low-medium — ncpu−1 sleeping threads per process (surprises fork/exec-heavy or thread-counting code); container `GC_get_nprocs` is cgroup-quota-unaware (consider `sched_getaffinity` on Linux). preview_mt already auto-starts markers, so this benefits **default builds only**.
- **Effort:** Small (1–2 days incl. fork hook + Linux CI verification).
- **Depends:** None. Amplifies #4 (stealable fiber-stack scanning), partially mutually exclusive per-collection with the incremental profile.
- **First measurable step:** 30-line patch + rerun the `gc_markers` probe workload and `std_spec`; verify `GC_get_parallel()` flips from 0 to >0.
- **Verifier evidence:** Replicating `boehm.cr`'s init sequence against homebrew libgc 8.2.12 gives `GC_get_parallel()`=0 and no env var fixes it; after `GC_start_mark_threads` parallel=7, full-GC 20.62→7.24 ms @160 MB. Fork child reset (`GC_parallel`=FALSE) and restart confirmed working. **Implementation correction:** `GC_set_markers_count` has no effect after init — call it *before* `LibGC.init`; gate the new funs for wasm32/win32/`VERSION < 8.2.0`.

### 2. Heap presizing + pacing defaults (initial-heap floor + `free_space_divisor` exposure)
- **What & where:** Three tiers — (a) document `GC_INITIAL_HEAP_SIZE`/`GC_FREE_SPACE_DIVISOR`/`GC_MARKERS` env vars (they already work); (b) bind `GC_set_free_space_divisor` and `GC_expand_hp` as `GC.free_space_divisor=`/`GC.presize_heap(bytes)` and honor a `CRYSTAL_GC_INITIAL_HEAP` env in `GC.init`; (c) consider an opinionated init heap floor (8–16 MB) for the perf fork. `src/gc/boehm.cr:211-224` does zero tuning today.
- **Mechanism + reference design:** bdwgc collects roughly every `heapsize/free_space_divisor` (=3) bytes; default initial heap is tiny. This is the **GOGC analog** (Go: doubling headroom halves GC CPU). Crystal forum #3997 confirms these are the official levers users currently can't reach without hand-written externs.
- **Corrected impact:** Allocation-heavy batch/compiler-like workloads **5–30% wall**, up to ~43% process CPU (measured: Crystal compiler frontend with `GC_FREE_SPACE_DIVISOR=1` went 6.4–7.9 s → 4.6–4.8 s real, max RSS unchanged at ~2.3 GB). 64M floor cut 81 collections to 1 for a 32 MB workload, adding only ~0.6 MB RSS. Low-allocation apps ~0. Windows env-var tier does not work (bindings tier required).
- **Risk:** Low — pure RSS-vs-CPU tradeoff; env-only tier is zero risk; an opinionated floor needs a small-process RSS audit.
- **Effort:** Small (bindings + docs ~1 day; default-floor experiment +1 day).
- **Depends:** None.
- **First measurable step:** Compiler-build + HTTP benchmark matrix over `GC_INITIAL_HEAP_SIZE` × `GC_FREE_SPACE_DIVISOR` using env vars only (zero code).
- **Verifier evidence:** Reproduced on the exact dylib Crystal links: 32 MB alloc → 81 GCs default (~405 KB/GC), `GC_INITIAL_HEAP_SIZE=64M` → 1 GC; `FSD=1` → 6 GCs. Apply `CRYSTAL_GC_*` *after* `LibGC.init` (the env read at init would otherwise overwrite an earlier setter). `GC_MARKERS` is inert on default single-threaded builds — hedge that in docs.

### 3. Precise-heap marking via a custom bdwgc kind (research track, with a Whippet backend spike as the endgame)
- **What & where:** Track A — register one custom kind (`GC_new_kind` + `GC_new_proc`) whose mark proc dispatches on the `type_id` word already at offset 0 of every class instance (`codegen.cr:2270-2273`) and walks compiler-emitted per-type pointer-offset tables (extend `has_inner_pointers?` at `types.cr:54-99` to full offset lists, Julia-style u8/u16/u32 arrays); route pointer-bearing classes to a new `__crystal_malloc_precise64`, keep pointer-free classes atomic. Track B — spike a `src/gc/whippet.cr` backend behind the pluggable seam (`gc.cr:139-143`, precedent `-Dgc_none`), starting from Whippet's bdwgc-compatible shim. Both consume the same per-type pointer-offset table.
- **Mechanism + reference design:** Conservative marking loads and range-checks every aligned word of every NORMAL object; a precise mark proc touches only real pointer slots, eliminating false retention from pointer-looking scalars. Reference designs: **Mono SGen, gcj's own design, Scala Native, Julia's offset arrays**; Whippet/Immix for Track B.
- **Corrected impact:** Track A: realistic **5–20% full-GC mark-time reduction** on mixed pointer/scalar heaps in benign workloads (the headline 4.4× / 75→17 ms is **adversarial-best-case only** — read it as a ceiling, not a typical gain). The durable win is **robustness** (no scalar-induced false retention), not raw throughput. Mutator-side allocation is **neutral-to-slower on stock libgc** until a vendored libgc raises `THREAD_FREELISTS_KINDS` (a custom kind has index ≥3, bypasses thread-local free lists, takes the global lock per alloc). Track B: speculative 1.5–3× MT allocation throughput per Whippet/Immix prior art, unverified for Crystal, ~30–40% odds of production parity within the stated horizon.
- **Risk:** Track A medium-high — global alloc-lock on stock libgc; mark procs must tolerate cleared free-list objects; union-typed ivars must stay conservative slots; **a wrong offset table = collected live object** (memory-unsafe). Track B high — Whippet is pre-1.0; must reach parity on finalizers, disappearing links, fiber hooks, fork handling.
- **Effort:** Track A large (codegen table emission + runtime kind + `std_spec` soak); Track B large (2–4 week shim spike, multi-quarter native integration).
- **Depends:** Track A's per-alloc fast path hard-depends on a vendored libgc with raised `THREAD_FREELISTS_KINDS`; Track B's native precise mode depends on Track A's pointer-layout tables.
- **First measurable step:** C shim + hand-written mark proc for one shape; benchmark conservative vs precise on a 100 MB `Hash(Int64,Int64)` / `Array(String)` heap.
- **Verifier evidence:** All cited bdwgc symbols (`GC_new_kind`, `GC_new_proc`, `GC_make_descriptor`, `GC_init_gcj_malloc`, `GC_gcj_malloc`) exist and are exported by homebrew 8.2.12 (`enable_gcj_support`=ON, `PARALLEL_MARK`=ON). Confirmed global-lock dependency: default `THREAD_FREELISTS_KINDS`=3, kinds ≥3 route to the locking global path. **New finding:** the gcj fallback's descriptor offset defaults to the *second* word (`GC_GCJ_MARK_DESCR_OFFSET`=ptr size) but Crystal's type_id is at offset 0 — the custom-kind path reads offset 0 freely (layout-compatible), only the gcj variant needs ABI changes. macOS MPROTECT_VDB is gated `!THREADS`, so generational mode is effectively unavailable on threaded macOS builds.

### 4. Stage-1 LLVM allocator attributes (codegen allocation-elimination track)
- **What & where:** Attach `noalias` return, `allocsize(0)`, `allockind("alloc,zeroed")` (NORMAL) / `allockind("alloc,uninitialized")` (atomic), and a shared `"alloc-family"` to `GC_malloc`/`GC_malloc_atomic` (and `__crystal_malloc64`/`__crystal_malloc_atomic64`), name-special-cased onto the LibGC extern declarations. `codegen.cr:2363-2429` (malloc fun creation), `:1334` (existing `add_attribute` machinery), `:14-16`. Stage 2 (medium): sink unconditional closure-env allocation (`:2054-2059`, `:2127-2167`) to first Proc materialization. Stage 3 (large, RFC-0004): Go-style escape pass lowering non-escaping `new`/envs to `alloca`.
- **Mechanism + reference design:** Optimized IR has a bare `declare ptr @GC_malloc(i64)` with zero attributes, so LLVM cannot delete dead allocations or fold memsets — exactly the attributes **Rust (`__rust_alloc`) and Swift (`swift_allocObject`)** emit. Honest caveat: real heap-to-stack lives in LLVM's Attributor, not the default O2/O3 pipeline.
- **Corrected impact:** Stage 1 **~0–1% macro** in release builds (not the originally hoped 0–3%); large wins only on microbenchmarks where non-escaping allocations vanish entirely. Stage 2: ~0–2% (most closured params are stored at entry, no legal sinking). Stage 3: 5–15% alloc-volume reduction plausible by Go analogy, 3–10% wall unmeasured anywhere, multi-month, RFC-0004-gated.
- **Risk:** Stage 1 medium-as-soundness — `allockind("alloc,zeroed")` must NOT go on the atomic variant or the c_malloc fallback; needs LLVM ≥15 gating; validate with `std_spec` at `-O3` + IR spot-checks. Stage 3 risks are memory-unsafe (conservative-stack growth, must exclude finalizable/`to_unsafe`/C-escaped/identity uses).
- **Effort:** Stage 1 small (1–3 days, 50–100 lines + LLVM≥15 gating — bindings lack `allockind`/string-attribute support today); Stage 2 ~1 week; Stage 3 multi-month.
- **Depends:** Independent; complements #5 (memset skip) — keep both since attribute folding only helps optimized builds. Stage 3 is the owned version of the acknowledged structural blocker.
- **First measurable step:** Add the minimal sound attribute subset, A/B the emitted IR at `-O3` for dead-alloc elimination, run `std_spec` at `-O3`.
- **Verifier evidence:** A/B-tested with LLVM 22.1.7 `opt -O3`: the minimal sound subset (noalias+allockind+allocsize+alloc-family) yields dead-alloc deletion and full elimination of non-escaping allocations. **Refuted sub-claim:** memset-into-zeroed-alloc folding for *escaping* pointers requires `memory(inaccessiblemem: readwrite)`, which is **unsound** for bdwgc+Crystal (the `GC_malloc` slow path triggers collection → runs Crystal finalizers and the fiber-stack-pushing start callback, i.e. writes module-visible memory). Recover that win via #5 instead.

### 5. Skip the redundant memset after NORMAL-kind `GC_malloc`
- **What & where:** In codegen, stop emitting the memset-to-zero after **non-atomic** `__crystal_malloc64`: `pre_initialize_aggregate` memsets the whole object (`codegen.cr:2266-2267`) and `generic_array_malloc` memsets the whole buffer (`:2350-2361`), but `GC_malloc` (NORMAL kind) guarantees cleared memory (`gc.h:651-655`). Keep the memset for the atomic path (PTRFREE is never cleared), the c_malloc fallback (preludeless), the `Reference.pre_initialize` primitive (`primitives.cr:829-838`, caller-provided pointer), and the `alloca` branch. Land behind a `-D` flag.
- **Mechanism + reference design:** Eliminates a full memory pass over every pointer-containing class instance and Array/Hash buffer. The zeroed-NORMAL contract is relied on the same way by **Mono/gcj clients**, and Crystal's own `gc/none.cr:13-24` clears explicitly to honor it. Distinct from roadmap Phase 9a (`malloc_uninitialized` for atomic pure-overwrite buffers): this targets the NORMAL path where zeroing already happened inside the allocator.
- **Corrected impact:** **~1.03–1.12× on the allocation op** (measured, `--release`: 32 B class ~1.03×, 1 KB buffer 1.07×, 8 KB 1.12×, 64 KB 1.08×) — about 3× less than the originally hoped 1.5×, because the duplicate memset runs over cache-warm memory and LLVM already shrinks per-object memsets. Macro **~0.1–0.5%** on allocation-heavy programs, ~0 for String/atomic-heavy code; possibly modestly higher on x86 Linux (lower memset bandwidth).
- **Risk:** Low-medium — the contract is documented and enforced by both backends, but every allocator path (gc_none, c_malloc, interpreter, any future inline fast path) must uphold it; a missed path = silent garbage in "zeroed" ivars. Flag-gated + `std_spec` + IR diff first.
- **Effort:** Small (1–2 days; a *threaded condition* in shared helpers, not a two-line deletion).
- **Depends:** Interacts with the allocation fast path (#9, rejected) — any inline path must also return cleared memory. Complements #4 (works at `-O0` too).
- **First measurable step:** Add the `-D` flag, diff emitted IR at one allocation site (the GC_malloc + redundant memset pair should disappear on the non-atomic path), run `Benchmark.ips` on `Array(String).new(n)` / Hash growth.
- **Verifier evidence:** Confirmed three ways the NORMAL contract holds (bdwgc `gc.h`, source enforcement in `malloc.c`/`reclaim.c`, Crystal `src/gc.cr:106` docs and `gc/none.cr` issue #14678). Double-zeroing confirmed in emitted IR at `-O0` and `--release` (`GC_malloc(48)` + `llvm.memset(44)`). The interpreter's `pointer_malloc` runs host-compiled `Pointer.malloc` (host always boehm), so the contract holds there automatically.

### 6. Skip the no-op shrink `GC.realloc` in `String.new(capacity)` / `String::Builder#to_s`

- **What & where:** Skip the trailing shrink `GC.realloc` at `src/string.cr:279-281` (`if bytesize < capacity`) and `src/string/builder.cr:108-111` → `resize_to_capacity` (`builder.cr:143-146`) **when bdwgc would reclaim nothing** — gated on a `GC_size`-based predicate (`GC.size` is already bound at `boehm.cr:163`). Keep the realloc unchanged for the genuinely-shrinking case and for `gc_none` (`src/gc/none.cr:37-49`). This resolves the roadmap's deferred "is shrink-within-size-class no-copy?" question.
- **Mechanism + reference design:** bdwgc `GC_realloc` shrink semantics (verified in `mallocx.c:165-178`, identical across 8.0.x/8.2.12/master): if `new_size ≥ slot/2` and it fits the current granule-rounded slot, it returns the **same pointer after `BZERO`-ing the tail** — reclaiming nothing while paying a cross-dylib FFI call + a tail memset that is pure waste for atomic (PTRFREE) string bytes; only below half does it `malloc`+copy+`free` and actually return memory. Builder growth is power-of-two, so the result usually lands in the no-op band.
- **Corrected impact:** **~3–5% on in-band string-construction microbenchmarks** (measured: skip saves ~6 ns of 185 ns for `String.new(1024)` at 90% fill; ~60 ns of 1.25 µs at cap 16384) — *not* the originally hoped 2–15%, and **0% at ~2× overshoot** where the realloc genuinely moves+reclaims and must not be skipped. Strongest real win: **large builders (≥64 KB…1 MB at ~53–99% fill, e.g. `IO#gets_to_end`)**, where the skipped tail `BZERO` is tens-to-hundreds of KB (~0.4–8 µs/call). Macro **<0.1–0.2%**. RSS delta is **exactly zero iff the `GC_size` predicate is used** (the naive `≥ capacity/2` predicate regresses RSS — see evidence).
- **Risk:** Low — depends only on documented/measured `GC_realloc` semantics, runtime-verifiable via `GC_size` in specs, behaviour-neutral otherwise (pointer identity preserved in the skipped case; atomic string bytes are unscanned, so a retained tail creates no false-retention risk).
- **Effort:** Small (~1 day: a Boehm-aware `should_shrink?` helper + two call sites + `Benchmark.ips` at 25/50/90% fill ratios).
- **Depends:** None for shipping; this **is the resolution** of the existing roadmap item "String::Builder#to_s shrink-`GC.realloc` (deferred pending size-class analysis)" — the analysis is now done.
- **First measurable step:** Add the `GC.size`-based predicate, then `Benchmark.ips` on `String.build`/`String.new(capacity)` across fill ratios; assert pointer identity and `GC_size` in a spec to pin the bdwgc behaviour against version drift.
- **Verifier evidence:** Shrink semantics reproduced on the exact linked dylib (homebrew 8.2.12) via C probes and `bin/crystal run` (`req 1024→600`: same ptr, `GC_size` 1024→1024, tail zeroed; `→100`: new ptr, size 112). **Three corrections fold in:** (1) the proposal's "simply `≥ capacity/2`" predicate is **wrong and RSS-regressing** — the half-rule is against the granule/**block-rounded** slot (req 2048→4096-byte block ⇒ no-op band starts at 100% fill; measured minimum no-op fill 73→54.8%, 1024→65.6%, 8192→75%, 16384→62.5%), so the predicate **must** use `GC_size` (lock-free header read, ~4.4 ns); (2) **no allocator lock is saved** on the small-object in-place path (the saving is FFI + header lookup + tail memset only); (3) the `<half` move path is a **net win today** (slot reuse: 104.6 ns vs 178.5 ns) and must be left untouched. The shrink behaviour is a stable bdwgc implementation detail, not a documented API guarantee (`gc.h` warns against relying on realloc internals) — hence the mandatory `GC_size` runtime guard.

## Rejected / downgraded

These were verified `confirmed=false`. Recorded with the specific refutation so they are not re-litigated.

- **Make GMP/BigInt limb memory pointer-free (`GC.malloc` → `GC.malloc_atomic` in `lib_gmp.cr:285-289`).** **REFUTED — reproduced heap corruption.** GMP routes *all* allocations through one global hook, persistent limb buffers *and* internal temporaries — it is all-or-nothing. GMP's `WANT_TMP_ALLOCA` build sends large temporaries (>~32 KB, used in big mul/div/FFT) through `__gmp_tmp_reentrant_alloc`, which **chains heap blocks via an in-block `next` pointer**; the only C-stack reference points to the newest block, so older blocks are reachable only through that next pointer. Made atomic, the GC never scans those pointers, reclaims the older chain mid-operation, and GMP's `TMP_FREE` then double-frees. Empirically: installing `GC_malloc_atomic` as GMP's allocator and forcing `GC_gcollect()` during a 2^24-bit `mpz_mul` produced an immediate bdwgc abort "Duplicate large block deallocation"; the NORMAL control ran clean. The proposal's "audit shows it's safe for limb buffers" is true for limbs but false for temporaries. The only safe route to pointer-free limbs is a *separate non-GC allocator* for GMP — a much larger design change, not a one-line hook swap.

- **Make suspended-fiber stack scanning stealable (`GC_push_all` instead of `GC_push_all_eager`, `boehm.cr:482-484`).** **REFUTED — crashes in exactly the regime it targets.** The mechanism is real (bdwgc itself defers registered thread stacks this way for parallel-marker stealing) and the impact is material (measured 1.42×@4KB, 1.52×@16KB, up to 2.5×@64KB dirty stacks with markers on; ~1.0× without markers). But in **all released 8.2.x** (homebrew, distro, Crystal's bundled libgc), the exported `GC_push_all` **ABORTs on mark-stack overflow** (`mark.c:1195-1205`, "Unexpected mark stack overflow") — graceful `MS_INVALID` recovery exists only for in-mark-loop pushes and only in unreleased master. Empirically: 3000 fibers OK, 5000 SIGABRT, **10000 fibers (the proposal's own benchmark) SIGABRT on first GC**. The internal `GC_push_all_stack` (with the headroom guard) is not exported, and 8.2.x exposes no API to query/pre-size the mark stack. Viable only re-scoped to a vendored/patched libgc or a capped hybrid (defer ≤~2000 stacks, eager remainder) — larger than "Small".

- **Vendor a fork-tuned static libgc "perf preset" (`DONT_ADD_BYTE_AT_END`, Darwin TLS patch, `THREAD_FREELISTS_KINDS=8`, `INITIAL_MARK_STACK_SIZE`, `HBLKSIZE=16384`+`DONT_PROTECT_PTRFREE`, LTO).** **REFUTED as scoped/estimated; ~0–2% shippable-by-default impact.** (a) Darwin TLS patch ~0%: measured `pthread_getspecific` 1.88–2.11 ns/call vs `__thread` 1.89–1.90 ns/call cross-dylib on this exact machine — no exploitable delta. (b) `HBLKSIZE=16384`+`DONT_PROTECT_PTRFREE`+`FILTER_PTRFREE`: 0% today because Crystal never calls `GC_enable_incremental` (those VDB paths never execute), and `HBLKSIZE=16384` adds 4× block-granularity fragmentation. (c) LTO inlining: unreachable — Crystal has no LTO pipeline and emits native objects, so libgc bitcode cannot inline. (d) `THREAD_FREELISTS_KINDS=8`: 0% until custom kinds exist. (e) `DONT_ADD_BYTE_AT_END` footprint: real but ~5–15% RSS (only exact-16n requests pay), **not shippable as default** — it makes an object whose only live reference is a one-past-end pointer (a pattern LLVM-optimized loops emit) collectible, an **undetectable false-COLLECTION/UAF hazard** (the proposed `GC_PRINT_BLACK_LIST` audit catches false *retention*, not false collection), and **no production bdwgc embedder (Mono, Unity, Nim, D, Julia) ships it**. Retains option value as an opt-in benchmark preset only.

- **Cheaper finalization via `GC_register_finalizer_no_order` (Phase 1).** **REFUTED by measurement.** Built `fin_compare.c` against homebrew 8.2.12: `ignore_self` (current) 0.341/0.348 s vs `no_order` 0.334/0.399 s for 2M objects — **no speedup, sometimes slower**. The dominant cost is per-object registration (lock + hash insert) plus the per-GC full fo-table walk, which both variants pay identically; the mark-proc difference is tiny for small objects. The proposal mis-cited bdwgc's `disclaim_bench` 6× figure, which is `no_order`-vs-disclaim, not `ignore_self`-vs-`no_order`. The "objects freed one cycle earlier" RSS claim was not observed at steady state (heaps identical). Switching also changes finalization ordering/visibility (a semver-sensitive behavior change). **Phase 2 (`GC_finalized_malloc`/disclaim) is real (~6.7× on its narrow target) but mis-located** — allocation happens in the `allocate` primitive (`codegen/primitives.cr:815-827`) before the finalize check, so it needs codegen threading; the disclaim kind shifts `GC_base`/`GC_size` by one word, breaking `WeakRef` disappearing-link registration; and the whole-program ceiling is <1% for typical apps.

- **Allocation fast path: `GC_malloc_many` pools (Phase 1) + inline `GC_FAST_MALLOC_GRANS` port (Phase 2).** **Premise refuted (named sites aren't allocations); feasible but downgraded.** The proposed Phase-1 hot sites — Channel `Sender`/`Receiver` (`channel.cr:51/67`), scheduler `Parked` nodes (`thread_pool.cr:10`), timers — are **`struct`s pushed by `pointerof` (stack), not heap allocations** (none call `__crystal_malloc`). The economic framing is also partly false: homebrew libgc is built *with* `THREAD_LOCAL_ALLOC`, so `GC_malloc` already amortizes the lock to ~1/refill internally — the "one lock per object" story describes what bdwgc already does. A Crystal-side pool at *genuine* hot fixed-size sites is real but narrow (~25–30% of allocation cost at converted sites, macro <1–2%). **Phase 2 (inline IR port) is net-negative-EV:** the proposal's own mechanism concedes ~0 single-threaded gain (7.85 vs 7.95 ns); the only real win amortizes Darwin's pthread-TSD lookup, which a Phase-1 pool already captures more safely, while a botched `EXTRA_BYTES`/granule computation in the IR port silently produces objects whose last pointer word is untraced (UAF). bdwgc's `gc_inline.h` itself says "Manual use is hereby discouraged."

- **Opt-in incremental/generational latency profile (lift the fork-handling veto, bind `enable_incremental`+`time_limit`, idle `collect_a_little`).** **Headline premise refuted on the shipping platform.** The claimed fork-veto (`"Can't turn on GC incremental mode as fork() handling requested"`) is guarded `#if defined(CAN_HANDLE_FORK) && !defined(THREADS)` — it exists only in the *single-threaded* build. The homebrew lib is the THREADS build; empirically, Crystal's exact `GC_set_handle_fork(1)` → `GC_INIT()` → `GC_enable_incremental()` sequence yields `GC_is_incremental_mode()`==1 with **no warning**, incremental stays on through 100k allocs + `GC_gcollect`. So the proposed `-Dgc_no_fork_handling` flag and "lift the veto" work item are **unnecessary** on macOS ARM64. The defensible subset survives: bind `GC.enable_incremental` + `GC.time_limit=` (note: `time_limit` defaults to UNLIMITED in `PARALLEL_MARK` builds, so enable alone bounds nothing — confirmed `GC_get_time_limit()`==999999) and wire idle `GC_collect_a_little` (its header explicitly endorses calling it in a wait loop). But it is a **latency-only, opt-in profile with a 5–20% throughput loss**, materializing only on large stable heaps with `time_limit` explicitly set; on macOS ARM64 `protection_needs`=3 (verified) means first-write faults via Mach round-trips hit even pointer-free buffers (wingo measured the analogous Guile mode +20% runtime). Ship only as a separate Linux-first profile; the central justification is refuted.
